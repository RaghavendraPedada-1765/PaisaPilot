# PaisaPilot - project context

On-device, UPI-first AI expense tracker. Flutter, Android first. Owner: Raghav.

## Rules
- Use the X: drive only for this project (code, SDKs, downloads, build caches where configurable).
- All user data stays on the device. No cloud sync in the MVP. The AI assistant runs on the phone (Gemma); a Claude API option, if added later, must be opt-in and send only what a question needs (see `docs/ai-agent-plan.md`).
- `data/` holds real bank transactions. Never commit or upload it.
- The GitHub repo (github.com/RaghavendraPedada-1765/PaisaPilot) is public. No personal data in committed files: test samples use made-up names, refs and account digits; personal categoriser keywords live in the git-ignored `data/personal_rules.json` (format: `personal_rules.example.json`). Build and test the app with `--dart-define-from-file=../data/personal_rules.json`, or the Self transfer / Family / College rules match nothing.

- SMS inbox import without a plugin: `MainActivity.kt` exposes the `paisapilot/sms` channel (hasPermission / requestPermission / readInbox since millis). `lib/import/sms_sync.dart` imports new alerts and stores the newest message time in the `settings` table (schema v2; the column is `name` because drift's parser drops a column called `key`). Sync runs on launch and on resume once access is granted; the sync button and the empty-Home button ask for access. READ_SMS is fine for sideloading, but Play only allows it for approved use cases. 32 tests pass. Works on Raghav's phone (vivo, Android 16) with no errors in logcat; vivo logs harmless `/proc/fas/render` avc denials.

- Parser coverage, checked on 16 Nov 2026 against the phone inbox (counts and masked outlines only, never message text). Canara alerts come in 6 formats: older `Acct … Dr./credited … UPI:`, `paid thru A/C … UPI Ref` (dd-mm-yy), `Your a/c no. … credited … (UPI Ref no …)` (m/d/yy, 12-hour time), balance-only `An amount of INR … DEBITED/CREDITED … Total Avail.bal` (dd/mm/yyyy, no payee or ref; about 1,250), and debit card POS/ATM. Also ICICI `Acct … debited for … credited. UPI:`, CGG Bank, and FamPay. slice card repayment SMS are imported as Self transfer on the card account (SMS parser v3). Not imported: money requests and mandate reminders. About 20% of balance-only alerts are twins of a UPI alert. The importer pairs them on account, direction, amount and date (and balance) in either order. Accounts match on bank name plus trailing digits (XX1595 = XXX595). Bump `SmsSync.parserVersion` whenever the parser learns new formats, so old messages are re-read once. 49 tests pass.

- Gmail import for slice alerts: `lib/import/gmail_source.dart` (google_sign_in 7, gmail.readonly, REST calls straight from the phone to Google) and `email_sync.dart` (query `from:slice.bank.in`, remembers the newest email read, `parserVersion` forces one re-read). Email text goes through `parseSms`. slice emails are for the slice savings account (source `slicebank`): UPI debits `₹X debited from your slice [bank ]account xx… via UPI. Transaction date dd-Mon-yy To NAME RRN …`, UPI credits `You have received ₹X via UPI in your slice bank account … From NAME RRN …`, other credits `… in your slice bank a/c … Ref No. …`, and card repayments (CR on the slice card account, categorised Self transfer). All 65 transaction emails parse; the other 4 are statement, OTP and promos. Google Cloud project "PaisaPilot": Android OAuth client (package `com.raghav.paisapilot`, debug key SHA-1 `9D:B5:75:77:96:14:54:4E:24:4F:B4:26:DB:0B:A9:20:4D:BD:D2:E1`) and a Web client whose ID is the `serverClientId` in the code. The consent screen is in Testing, so the grant expires every 7 days and the app asks to reconnect. A release build needs its own SHA-1 added. Connect from the ⋮ menu. Once, after an update, the app showed Gmail as not connected; the cause is unknown, and reconnecting fixed it. 61 tests pass.

- Statement PDF import on the phone (⋮ → Import Canara statement PDF): file_picker → pdfrx (PDFium) → `lib/import/pdf_text.dart` `layoutText` rebuilds `pdftotext -layout`-style text → `parseStatement`. Lessons from the real e-passbook: take words from PDFium's text order, not from glyph gaps (glyph boxes hug the ink); group rows by each run's typical letter (`**` in masked VPAs sits high); characters with empty boxes (often at 0,0) follow the previous one; PDFium splits amounts after the decimal point (`1,234. 56`), so `_joinNumbers` rejoins them. On the phone this gives 467 rows, 0 bad, 0 balance mismatches, and 461/461 UPI rows with 12-digit refs, the same as the Python parser. The import shows a preview (row count, balance mismatches) before writing. After the import it reconciles: the account's rows in the app over the statement's dates must equal the statement's count, otherwise a dialog flags possible duplicates or missing rows. The result also says how many balance-only SMS rows got payee names. First real import (16 Nov 2026): 0 new, 467 already recorded. The reconciliation then found 1 extra row: an SMS-charges debit with no ref, whose SMS balance differed from the statement's running balance, so balance matching failed and the statement row was added next to the SMS row. Fixed: a ref-less statement row takes over a ref-less SMS row with the same account, date, direction and amount (source becomes 'statement', one claim per SMS row), and a ref-less SMS that matches a ref-less statement row is treated as known. Raghav deleted the duplicate by hand (the transaction sheet now has Delete), and the re-import shows 467 in statement = 467 in PaisaPilot. 74 tests pass; the account comes from the header number or the user's pick; PDF passwords are asked for and never stored. 68 tests pass.

- Activity: category tabs (All, Unsorted, one per category; swipeable), a "Largest first" sort, and a camera icon on rows with photos. The `activity` query takes `(direction, category, search, byAmount, maxRows)`; category NULL = all, 0 = unsorted.
- Transaction photos (schema v3, `attachments` table: txn_id with ON DELETE CASCADE, file_name, added_at). image_picker (camera or gallery) → `lib/data/photo_store.dart` copies them into the app's private documents folder `photos/`; the database stores only the file name. Deleting a transaction or a photo removes the files. `android:allowBackup="false"` and `fullBackupContent="false"` are set in the manifest, so Android Auto Backup no longer copies data to Google Drive (it was on until 16 Nov 2026). 80 tests pass.
